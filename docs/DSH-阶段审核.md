# 阶段自检与自动继续

S1–S5 各自保留一个后端审核记录。每轮重新检查真实保存的产物及当前计划绑定，检查通过后等待用户 60 秒，共三轮。三次等待完成、产物检查通过且没有待处理用户指令时，后端记为 `elapsed`，Host 唤醒同一个会话继续生产。正常情况下等待共 180 秒，检查耗时另计。

用户可以在工作台提前继续，仍需通过产物检查。明确暂停、未处理指令、自检失败都不会因超时放行。自检失败返回具体原因，修复后使用 `benchforge_stage_review(action=retry)`。`acknowledge` 只处理已应用的用户指令，恢复原有轮次，不代表模型能够自行提前批准。

普通执行绑定、同角色的一一改名、缩小几何例外、软摘要及其修订记录沿用原审核和已完成等待。自动修复不能删除原硬要求、关闭原生采集或机器人要求、移除明确要求的资产身份；修改这些要求须来自经过核验的用户编辑或新任务。其他合同变更仍建立新审核。

## 代码边界

| `src/dsh/host/stage_reviews.mjs` | 通过公开 subprocess 服务调用后端，随插件卸载终止调用 |
| `src/dsh/production/lifecycle.mjs` | 按会话安排定时器，通过公开 `steer` / `followup` 续跑，去重并保留用户取消 |

## 并发与恢复

检查使用每个审核独立的操作系统锁，PostgreSQL 事务只在提交审核状态时持有行级锁。多个工具、浏览器或 Host 同时观察不会增加轮数。检查期间到达的暂停、指令、计划修订或新阶段使旧检查结果失效。进程退出释放检查锁；重启读取已保存轮次。停机期间不能伪造检查，也不倒填尚未执行的等待。

Host 通过已认证的 `/stage-review/read` 读取 PostgreSQL 已提交快照，不持有审核写锁，不缓存放行结果；单次读取默认最多 10 秒，并响应用户停止。`reviewReadTimeoutMs` 由生产、采集和审核策略插件配置。后端不可用报告 `BENCHFORGE_REVIEW_STORAGE_UNAVAILABLE`，不把存储故障误报为等待用户确认。审核策略在公开 `tools/execute` 扩展点异步读取最新记录，DSH 同步 `tools.guard` 不承载异步查询。

旧的已放行记录保留原结果；旧的未完成审核在第一次后端访问时迁移，从真实自检开始，不伪造历史检查次数。发布前备份审核数据库、会话存储和本地配置。浏览器关闭或模型结束本轮后，Host 定时器仍可推进当前审核。

## 生产准备与停止

工作台提交的明确生产请求在读取合同、准备计划时即进入生产投影，不依赖首个成功的计划回执。模型最后一条回复没有可见正文，或尚无交付与真实等待、受阻记录时，Host 通过 `agent/turn-stopping` 请求继续。同一轮次和业务状态默认最多恢复两次，仍未推进则显式报错并展示“任务未完成”；重放保留已消费的恢复通知，普通聊天不受此策略影响。

用户停止会打断排队中的阶段检查，撤销本轮后台检查和定时续行。晚到的后端结果不能重新唤醒会话。Python 工具与阶段检查的子进程收尾默认最多等待 5 秒，阶段检查本身默认最多 15 秒；未确认清理完成须报告错误并保留进程所有权，不能将超时当成退出成功。通用等待放在 `src/dsh/runtime/cancellation.mjs`，进程所有权与释放放在 `src/dsh/host/process_cleanup.mjs`，业务状态仍由生产投影和审核后端管理。

## 采集完成后的续行

采集提交工具返回 `submitted`、`submission_accepted=true` 和 `scene_acceptance=pending`，只表示请求已受理。Host 自动登记按会话和运行编号持久化的后台观察；不再依赖模型记得调用 `benchforge_wait(background=true)`。工具返回之后才到达的成功或失败结果，通过标准用户消息及公开 `steer` / `followup` 唤醒原会话。登记失败仍返回已提交作业的身份，恢复跟踪时不得重复提交采集。

`src/dsh/tools/scene/capture/capture_runtime.mjs` 持有 `storageDomain`、服务客户端及插件生命周期；`continuation.mjs` 负责观察、重试交接、结果去重与续行；`continuation_state.mjs` 从标准 Native/PTC 工具事件恢复归属。重载恢复未完成观察，已消费的通知不重放；修复中因服务卸载而中断时，按该次中断编号另发一次恢复通知。用户暂停、取消、新任务和已完成流水线不会被旧采集通知重新驱动。多个运行独立观察，同一运行的重试切换代次并终止旧的状态查询，不取消实际服务作业。

采集验收失败必须读取实际缺项，保留硬要求及可辨识资产，修复完整程序并重新采集。只写“下一步修复”不能结束生产义务。采集成功后仍须继续实际流水线或进入对应阶段审核。确有外部阻塞，或同一场景连续两轮失败项没有改善时，使用 `benchforge_scene_blocker` 保存所属服务作业的证据、具体原因和缺失条件；这不会将失败场景改为通过。连续三次尝试收尾且没有新采集提交或后续阶段回执时，Host 记录执行受阻，停止自动催促并要求明确报告未完成。预算随记录持久化；检查、空命令和重载不会重置预算，正常修复期间不限制工具数量或工作时长。

首次结果通知只提供去重摘要和完整证据入口，后续提醒不重复注入报告。`notice.mjs` 只负责通知格式，完整回执由原服务保留。场景设计可用与 `hard_requirements` 等长的 `requirement_stages` 指定 S2–S5；旧计划默认 S2，场景审图只检查 S2，后续原生采集仍按生产合同验证。`object_roles.representation` 可指定 `native_asset` 或 `articulated_robot`，这些对象不能进入几何例外；要求机器人运动的新场景必须声明机器人资产角色。

后台状态查询最多连续重试三次，再通知原会话恢复跟踪，避免网络故障触发无限重试。工作台只读取 `benchforgeProduction` 投影，显示等待采集、需要修复、继续生产、跟踪异常或受阻；浏览器不判断验收、不持有续行计时器。回归测试包括“对话先结束、失败后到达”、重载恢复、并发重试、通知去重、取消和新任务隔离。
